## Architecture decisions and design gates

The accepted outbound addition UR-070/TR-058 publishes explicitly opted-in,
committed Roadmap closures after push/merge to `master`. See
[ADR-0013](../architecture/adr/0013-publish-committed-github-closures.md) and the
[operator guide](../user_guide/GITHUB_CLOSURES.md). It supports outcomes 8–9;
GitHub-originated closures remain in the separate 0.5 scope. Implementation and
simulated tests do not replace the pending live post-merge publication proof.

[ADR-0011](../architecture/adr/0011-optional-requirements-and-governance.md)
records the accepted direction under ADRs 0001–0010. Domain and Application
remain standard-library-only; inbound/outbound adapters stay independent;
Bootstrap owns wiring. Markdown is canonical, SQLite is rebuildable. No graph
framework, provider sync service or new authentication service is required.

Before implementation, record reviewed examples and settle these details in the
corresponding work items:

- Readable-key allocation and explicit collision resolution across Git branches.
  UUID identity must survive an alias rekey; collisions fail closed.
- The acceptance-bearing fields and fingerprint canonicalization, including
  semantic versus formatting/metadata-only edits and manual edits.
- The transition table, evidence schema and history retention; no status can
  bypass acceptance/evidence prerequisites.
- The fixed relation vocabulary, canonical owning side and cycle rules.
- Recommendation eligibility, priority order/weights and stable tie-breaker.
- Schedule anchor/time semantics (recommended continuous UTC hours), unknown
  propagation, outside-scope predecessors and deadline variance presentation.
- Additive workspace schema/version boundary, downgrade behavior and CSV cutover.
- The read-only hosting URL command contract and supported remote shapes.

Accepted principles do not imply that these unresolved interfaces are settled.

## Delivery order and gates

1. **Establish real governance now.** Repair and audit the workspace, capture the
   GitHub baseline, create the current release milestone and work items, record
   observations with the installed CLI. This planning pass completes this gate
   without claiming 0.4 features are delivered.
2. **Identity and persistence.** Decide the record envelope/alias/fingerprint
   contracts; implement create/view/list/update through existing transaction and
   projection boundaries. Prove preservation and conflict behavior.
3. **Lifecycle, evidence and relations.** Implement explicit transitions,
   revision-bound evidence and typed ownership; prove invalid changes fail
   atomically and rebuilt reverse queries agree.
4. **Decision support.** Build gap queries, then next-work policy on those facts.
   Reconcile terminal/JSON counts and explanations against worked examples.
5. **Schedule and hosting URL.** Deliver the declared scheduling model and
   read-only URL contract. Compare rendering approaches before optional export.
   These can proceed once their independent design gates are settled.
6. **Adoption and release proof.** Exercise issue-only and requirements-enabled
   installed-package journeys; perform the authoritative register cutover only
   after preservation/verification succeeds. Finish baseline GitHub dispositions,
   audit later arrivals separately, run the self-hosted release journey and
   required packaging/documentation/compatibility checks.

GitHub triage and reproducible fixes may proceed alongside these phases. A bug
fix need not wait for the requirements feature to exist. No delivery date or
capacity estimate is invented; work item estimates remain unknown until assessed.

## Existing evidence and its limits

The [two-clone verification](collaboration-verification-2026-10-09.md) establishes
valid completion-after-pull reads and records the body-conflict refusal fix,
installed candidate proof and permanent installed-package CI journey.

The published [0.3.1 verification](../releases/0.3.1-verification.md) establishes

fixture. Those are enabling evidence, not verification of the new outcomes.
The existing longest-path calculation and default estimates do not prove the
new full scheduling contract. Historical placeholder GitHub issues do not prove
that their broad performance claims have been met.

[Work items and the GitHub baseline](0.4.0-work-items.md) provide the executable
plan. [Dogfooding observations](dogfooding-2026-10-08.md) record real commands,
health findings, repair and remaining friction. Read requirement status and
specific evidence, not milestone names or test coverage alone.

## Scope reconciliation

UR-051/UR-054 and TR-039/TR-043 are promoted from Deferred to Accepted for the
minimal lifecycle/evidence scope. UR-062–UR-066 and TR-048–TR-054 add the accepted
editing, recommendation, adoption, dogfooding, closeout and schedule contracts.
The larger proposal's CSV interchange, archive/supersession, scope-selection
and broader end-to-end journey remain Deferred (UR-055–UR-057, UR-059 and
associated technical rows). A one-time register cutover does not imply general
CSV interchange. Provider sync, GraphQL, AI insights, automatic hooks, dashboards
and capacity planning are not added by this acceptance.

## Completion criteria for 0.4.0

All nine outcomes and retained release commitments have concrete scoped evidence;
new work links intent or justified maintenance; installed-package adoption and
recovery journeys pass; the baseline has no omitted or unresolved external
issue; each not-planned disposition retains its rationale and does not count
as implemented requirement coverage. Review open dogfooding friction and the
compatibility/deprecation inventory before tagging or publishing 0.4.0.

## Accepted collaboration and import additions — 2026-10-08

gaps. Implement bounded complete GitHub import before substantial remaining
baseline closeout, then use it throughout dogfooding. These extend the original

integration decision under ADR-0002.
