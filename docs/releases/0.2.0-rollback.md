# Roadmap 0.2.0 rollback plan

PyPI releases cannot be replaced in place. Rollback means stop distribution,
restore user data from a known pre-migration copy when necessary, and publish a
new fixed version; it never means reusing the 0.2.0 version number.

## Before publication

If any final gate fails, do not tag or publish. Fix forward on the candidate
branch, rebuild from a clean commit, and repeat the complete release checklist.

## After publication

For a packaging or runtime defect:

1. Mark the affected PyPI release as yanked with a concise reason. Do not delete
   it unless it contains a credential or legally sensitive material.
2. Stop promoting the release and record the affected commands, platforms, and
   workspace schema states.
3. Reproduce from the published artifact, not the source checkout.
4. Fix forward to 0.2.1, rerun the complete artifact and cumulative migration
   gates, and publish through the same trusted workflow.

For a migration or canonical-data defect:

1. Tell users not to rerun mutation or repair commands.
2. Preserve the failed workspace and command output for diagnosis.
3. Restore the complete pre-migration `.roadmap/` tree from Git or backup.
4. Reinstall `roadmap-cli==0.1.1` until the fixed release is available.
5. Never combine a restored 0.1.1 SQLite database with partially migrated 0.2
   canonical documents. Restore the workspace as one unit.

SQLite projection corruption alone does not require data rollback. Canonical
documents remain authoritative; use health preview and projection rebuild after
the responsible code version is known safe.

## Decision record

Record the incident, published/yanked versions, affected workspace versions,
canonical digest evidence, recovery result, and owner in a repository issue or
release postmortem. A rollback does not weaken migration fixtures or suppress a
failing regression test.
