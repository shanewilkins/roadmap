## Intent
Maintenance: evaluate whether Pydantic improves requirements-file validation and diagnostics enough to justify a runtime dependency. Supports the existing durable requirements and preservation contracts (UR-049, UR-062, TR-038, TR-048, TR-049).

## Scope
Pilot explicit Pydantic schemas for YAML/frontmatter parsing in roadmap/adapters/outbound/persistence/requirement_documents.py. Convert validated input into the existing domain dataclasses. Keep Domain and Application standard-library-only and retain all business invariants there. Review coercion/strictness, supported legacy inputs, timestamps, and unknown-field handling explicitly. Preserve Markdown, unknown frontmatter, UUIDs, revisions, acceptance/evidence history and conflict/recovery behavior. Broader parser migration and GitHub response schemas are follow-up decisions based on the pilot.

## Acceptance and evidence
- Compare the existing parser with the pilot using representative valid, malformed, legacy and future/unknown-field fixtures; demonstrate field-level diagnostics for nested failures.
- Prove canonical round trips, reads without writes, manual-edit staleness and projection rebuild retain the current contracts. Reject malformed data without silent coercion or data loss.
- Record before/after validation and mapping complexity plus CLI startup/parsing measurements; judge whether duplicated schema/domain definitions and maintenance costs are justified.
- Document the dependency decision and owning persistence boundary under docs/architecture/dependency-boundaries.md. Any retained dependency must pass packaging, security, typing and supported-platform checks without broadening core import rules.
- Record an evidence-backed adopt/revise/drop recommendation. Keep the dependency only if the pilot demonstrates sufficient benefit; do not convert models across the project as part of this item.
